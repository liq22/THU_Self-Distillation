# spec-driven 论文写作工作流

> 来源: 从神经符号 PHM 综述的写作实践提炼 (源卡片 os_cards/017)
> 整理日期: 2026-07-09
> 适用范围: 用规格 (spec) + goal 包 + Codex/Claude 协作来驱动论文写作的可复用方法论;论文正文与 goal 包原件为私有指针

## 边界说明

这页是**方法论复盘与可执行清单**, 不是某个具体论文的写作日志。它从神经符号 PHM 综述的产出过程中抽象出"spec-driven 写作"的通用流程, 适用于任何需要长周期、多轮迭代、人机协作的论文 (尤其综述与长文)。论文正文、goal 包内容、协作日志均属敏感/大体积原件, 公开页只记**流程 + 结构 + 指针**。

---

## 场景

写一篇高水平综述 (神经符号 PHM 综述), 内容横跨故障诊断、RUL、跨域迁移、Agent 四个子方向, 体量大、结构复杂、需要多轮迭代与人机协作。如果直接自由起草, 极易陷入"写到一半发现分类体系不成立"或"返工牵连全文"的泥潭。

## 当时的问题

长文写作的典型痛点:

- **结构先行缺失**: 没有先固定分类体系和大纲就开始写正文, 写到中段才发现框架要推倒重来。
- **迭代不可追溯**: 改了哪一版、为什么改、谁 (人 / Codex / Claude) 改的, 没有统一记录, 返工时找不到决策依据。
- **协作无契约**: 人与 AI 协作时, AI 不知道这次任务的目标边界 (是改文字? 补文献? 还是改结构?), 容易越界改坏正文。
- **就绪状态不可判**: 投稿前/返修前"到底准备到什么程度了"靠感觉, 没有客观检查点。

## 为什么会发生

论文写作默认被当成"创作"而非"工程"。但综述这类长文, 其复杂度已经接近一个软件项目: 有结构 (大纲)、有依赖 (各节相互引用)、有版本 (多轮修改)、有多个"编译目标" (submission_ready / review_response_readiness)。用纯创作的方式管理工程级复杂度, 必然在结构、追溯、协作、就绪判定四个点上失控。

解法是把**软件工程的 spec-driven 思想**搬到论文写作上。

## 后来怎么解决

在神经符号 PHM 综述仓库 (`P03_nesy_phm_review/`) 里落地了一套 spec-driven 流程, 核心是三件套:

### 1. `.specify/` — 规格先行

在写正文之前, 先固定**规格层**: 综述的分类体系、每节的论点、文献覆盖范围、章节依赖。规格是"契约", 正文是"实现"。规格没定稿前不写正文。

### 2. `goal/codex_goal_*` — goal 包作为可执行任务单元

把写作目标拆成命名的 **goal 包**, 每个 goal 包是一个可交付、可校验的任务单元:

- `codex_goal_submission_ready_phm_nesy` — "投稿就绪"这一目标的所有检查点与任务清单。
- `codex_goal_air_review_response_readiness_phm_nesy` — "评阅意见回复就绪"这一目标的任务清单。

goal 包给协作方 (Codex / Claude) 一个**明确的任务边界**: 这次只做这个 goal, 不越界动别的。详见 [[canonical_skills注册表方法论]] 中"目标即注册项"的思想。

### 3. `specs → goal → logs → paper` 的流水线

写作按固定流向推进:

```
specs (大纲/规格)
  → goal/codex_goal_* (拆解成可执行 goal 包)
  → logs (Codex/Claude 协作日志, 可追溯)
  → paper (LaTeX 正文, 最后产出)
```

这与 [[论文流水线5步法]] 的流水线思想一致: 前一道工序的产物是后一道工序的输入, 每道工序都有可校验的中间产物。

### 配套: 文献的 arxiv_package 模式

参考文献不是散 PDF, 而是打包成版本化的 `arxiv_package` (`phm_nesy_phm_arxiv_package/main.pdf`), 便于批量追溯与引用稳定性。这与 [[对象分层与控制平面]] 中"资产分层管理"是同构的: 文献是一层, 正文是一层, 互不污染。

## 抽象原则

1. **规格优先于实现**: 长文先定结构 (大纲 + 分类体系 + 论点) 再写正文; 规格是契约, 正文是实现。
2. **目标即注册项**: 把模糊的"把论文写好"拆成命名、可校验的 goal 包 (submission_ready / review_response_readiness ...), 每个 goal 有明确的就绪判据。
3. **协作靠契约不靠自然语言**: 给 AI 协作方一个 goal 包边界, 比用自然语言描述"帮我改一下"安全得多 — 边界即护栏。
4. **流水线可追溯**: specs → goal → logs → paper 的每一步都留中间产物, 返工时能定位到具体工序, 而不是对着最终稿猜。
5. **资产分层**: 文献、规格、日志、正文各占一层, 不互相内联, 大体积资产走指针。

## 可执行清单

- [ ] 在论文仓库根放 `AGENTS.md` + `README.md` + `.specify/`, 让任何协作者 (含 AI) 第一时间读到规格与边界。
- [ ] 写正文前, 先在 `specs/` 固定分类体系与每节论点; 规格未定稿不进 `paper/`。
- [ ] 把"投稿就绪""返修就绪"等里程碑拆成 `goal/codex_goal_<milestone>_<shortname>` 包, 每个包内列检查点。
- [ ] 每次 Codex/Claude 协作只指派一个 goal 包, 禁止跨 goal 越界改稿。
- [ ] 协作过程落 `logs/`, 记录谁改了什么、为什么改 (决策依据)。
- [ ] 文献走 `arxiv_package` 打包模式, 不在仓库里散放 PDF。
- [ ] 投稿/返修前, 用对应 goal 包的就绪判据做客观检查, 不靠感觉。
- [ ] 综述仓库整体 (含正文/文献/日志) 作为大体积资产走私有指针, 公开复盘只写流程。

## 适用边界

- **适用**: 综述、长会议论文、博士论文章节这类结构复杂、多轮迭代、需要人机协作的长文。
- **不适用 / 过重**: 短文 (workshop / short paper)、纯计算/实验报告类、一次性快稿 — 这类直接写更快, 套 spec-driven 反而是流程税。
- **前置条件**: 需要熟悉 `.specify/` 与 goal 包的写法, 且仓库已有 `AGENTS.md` 约定; 否则先从 [[canonical_skills注册表方法论]] 入门再落地。

## 最容易卡住的地方

- **把规格当摆设**: 写了 `.specify/` 但中途不更新, 规格和正文脱节, 流水线名存实亡 — 规格必须随迭代同步修订。
- **goal 包粒度太粗**: 一个 goal 包塞进"投稿就绪"全部子任务, 等于没拆; 要拆到单次协作可完成的粒度。
- **跨盘指针失效**: 源仓库在 `<K盘>/`(工作盘), 公开页引用时走私有指针并校准实际落盘位置, 不直接拷工作盘路径。
- **AI 越界改稿**: 不给 goal 边界就让 AI 自由改正文, 容易把规格外的改动混进来 — 必须先指派 goal 包再协作。
