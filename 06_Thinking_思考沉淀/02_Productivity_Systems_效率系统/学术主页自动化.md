# 学术主页自动化

> 来源: 博士毕业源仓库 os_cards/020_个人主页与CV.md（ jemdoc + Jekyll + Google Scholar crawler 部分）
> 整理日期: 2026-07-09
> 适用范围: 个人学术主页（jemdoc 静态站 + Jekyll/GitHub Pages 站）的论文列表自动同步与流量监控

---

## 边界说明

这页是**自动化方法与可复用工程经验**，不是主页正文、不是 crawler 全部源码。

- 是什么：jemdoc 静态主页和 Jekyll 站点如何分工、Google Scholar crawler 如何把"发论文 → 主页更新"半自动化、Google Analytics 如何监控主页流量。
- 不是什么：不含主页 HTML/CSS 全文、不含 crawler 完整实现（源卡片只给到结构指针，细节以私有区源码为准）。CV 内容、个人照片、源码全部走私有指针。
- 本页是 [[CV与主页维护指南]] 的"工程下游"姊妹页：那页讲"维护什么"，本页讲"怎么让维护自动化"。

## 适合谁读

如果你是有持续发表节奏、需要一个可自动同步的对外学术主页的研究者（清华机械系或相关方向的博士 / 博后 / 青年教师），这页是给你看的"主页自动化"工程经验。

## 读完能做什么

- 理解 jemdoc 主站（稳）与 Jekyll 个人站（可自动化、可迁移）的双站点分工逻辑，知道为什么长期身份资产必须落到自己可控的 GitHub Pages。
- 拿到"Google Scholar crawler + GitHub Actions"半自动同步论文列表的思路，让"发论文 → 主页更新"变成一个动作。
- 知道在哪里接 Google Analytics 给静态主页补反馈环，并用可执行清单判断自动化是否落地。

## 场景

博士期间维护一个对外学术主页（清华机械系个人主页 + GitHub Pages 个人站）。核心痛点：每发一篇论文都要手动改主页 HTML 的论文列表、改 CV、同步 Google Scholar，**人工维护迟早漏更、版本错乱**。源仓库里沉淀了一套"jemdoc 主站 + Jekyll 个人站 + Google Scholar crawler"的工程基础，专门用来把这件事半自动化。

## 当时的问题

1. **论文列表手动维护**：发新论文要改 HTML、改 CV、改 Scholar 三处，容易漏改或不同步。
2. **静态主页无数据反馈**：不知道谁在访问主页、从哪来，投简历 / 申博后时无法判断主页的曝光价值。
3. **学校主页不可控**：jemdoc 挂在系域名下，部署受限、毕业可能失效，需要一个自己完全可控的站点兜底。

## 为什么会发生

学术主页本质是一个**内容更新频率低、但每次更新都不能漏**的静态站点。这种场景下：
- 纯手动维护违背"发论文和更新主页应是一个动作"的原则，导致主站与实际发表脱节。
- 没有流量数据，主页就退化为"摆设"，无法支撑求职 / 国际合作的决策。
- 把身份资产全部压在学校的不可控基础设施上，毕业即失效。

根因是：**主页既是内容资产又是身份基础设施**，对它既要"内容自动同步"又要"载体自主可控"，这两点分别由 crawler 和 Jekyll 个人站解决。

## 后来怎么解决

### 1. 双站点分工：jemdoc 稳 + Jekyll 新

| 站点 | 角色 | 自动化程度 |
|---|---|---|
| jemdoc 主站（系域名） | 官方对外名片，求稳 | 低（手动 + jemdoc 编译） |
| Jekyll 个人站（GitHub Pages） | 可自动化、可迁移的长期身份资产 | 高（crawler + GitHub Actions） |

分工逻辑：主站只在重大节点（新论文 / 新荣誉）手动改；个人站接 crawler 做"论文列表半自动同步"，作为长期主版本。毕业后若学校主页失效，个人站接管。

### 2. Google Scholar crawler 半自动同步

个人 Jekyll 站内集成 `google_scholar_crawler`（源仓库 `Richie_Li.github.io-main` 内），核心思路：

- **抓取**：定时从 Google Scholar 个人主页抓已发表论元数据（标题 / 作者 / 年份 / venue / 链接）。
- **落库**：生成站点可读的数据文件（如 Jekyll 的 `_data` 或 markdown 条目）。
- **渲染**：Jekyll 构建时把论文列表自动渲染到页面，无需手改 HTML。
- **触发**：配合 GitHub Actions 定时构建，实现"Scholar 更新 → 站点自动重建"。

> 注：源卡片只给到"集成 google_scholar_crawler"的结构指针，未含 crawler 完整实现细节。具体脚本、Scholar 反爬策略、字段映射见私有区源码（指针见末尾）。

### 3. Google Analytics 流量监控

主页接入 Google Analytics，监控：
- 访问量、来源（直接 / 搜索 / 引用链接）。
- 访客地理分布（对国际合作 / 求职地域决策有用）。
- 哪些页面 / 论文被点得多（反推哪篇工作受关注）。

价值：投简历或申博后前后看一眼 Analytics，能判断主页的曝光是否值得附在申请材料里，以及哪篇代表作最该置顶。

## 抽象原则

1. **把"内容更新"和"载体重建"解耦**：论文元数据进数据源，站点由构建器自动渲染，避免手改 HTML。
2. **身份资产必须自主可控**：长期身份信息（论文列表 / CV 链接）落到自己完全可控的 GitHub Pages，不全部依赖学校基础设施。
3. **静态站点也能有数据闭环**：用 Analytics 给静态主页补上"反馈环"，让它从摆设变成可度量的身份资产。
4. **发论文和更新主页应是一个动作**：通过 crawler 让"发表"这个事件自动触发"主页更新"，消除手动漏更。

## 可执行清单

- [ ] 个人 Jekyll 站已在 GitHub Pages 可访问，且为长期主版本。
- [ ] `google_scholar_crawler` 已集成，论文列表由数据驱动渲染（非手写 HTML）。
- [ ] 配 GitHub Actions 定时构建，Scholar 更新后站点自动重建。
- [ ] 主页已接入 Google Analytics，能看访问量 / 来源 / 地理分布。
- [ ] jemdoc 主站与个人站论文列表一致（主站稳、个人站新）。
- [ ] 毕业前已确认个人站可脱离学校环境独立存活（链接不依赖系域名）。
- [ ] crawler 源码、Analytics 配置、站点源码**没有**进公开 git（在私有区）。

## 适用边界

- **适用**：有持续发表节奏、需要一个可自动同步的对外学术主页的研究者（博士 / 博后 / 青年教师）。
- **不适用**：完全不会碰 Jekyll / GitHub Actions 的人（需先有静态站点搭建基础）；以及对 Google Scholar 反爬稳定性要求极高的场景（Scholar 反爬可能间歇失败，crawler 需有容错 / 人工兜底）。
- **诚实说明**：源卡片对 jemdoc 主站和 Google Analytics 只给了"集成"级别的结构信息，crawler 的实现细节（脚本 / 字段映射 / 反爬处理）未在卡片中展开，本页相应只写到"方法 + 思路"层面，实现细节以私有区源码为准。

## 最容易卡住的地方

1. **Scholar 反爬导致 crawler 间歇失败**：Google Scholar 对高频抓取会限流 / 弹验证码，crawler 必须有重试 + 人工兜底，不能假设它永远稳。
2. **把自动化当成"全自动"**：crawler 只解决"论文元数据同步"，CV 正文 / 方法图 / 联系方式仍需人工判断，不要期待站点完全无人维护。
3. **主站和个人站职责漂移**：自动化只做个人站，主站仍手动；若两边都接 crawler 反而会导致冲突和不同步。
