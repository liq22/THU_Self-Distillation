# 对象分层与控制平面

> 来源：博士毕业源仓库 os_cards/018_LQQL_OS自蒸馏OS.md（治理观提炼）
> 整理日期：2026-07-09
> 适用范围：个人科研知识系统的目录治理与平面划分原则

## 边界说明

这页是**科研治理观**——回答"个人知识系统的目录该怎么分、谁管谁"。

- 是什么：把"先分对象再分主题 / OS 是 control plane / 项目 repo 是 data plane"这套判断准则写清楚，作为建仓和迁移时的第一性原则。
- 不是什么：不是 LQQL_OS 全仓目录转写（那是方法论页 [[LQQL_OS自蒸馏OS方法论]] 的事），不是 skill 清单，不是具体论文流水线。

## 核心判断

科研知识系统长期维护的最大敌人不是"内容不够多"，而是**结构被污染**：待办混进知识树、执行内容塞进规则目录、raw 被改写导致溯源断裂。这套治理观用两条原则治本：

1. **先分对象，再分主题。**
2. **OS 是 control plane，项目 repo 是 data plane。**

## 先分对象，再分主题

个人知识系统同时要承载"待办、战略、知识、项目、agent 规则、归档"等性质完全不同的东西。如果顶层按**主题**分（比如"机器学习 / 机械工程 / 写作"），会发生两件事：

- 待办、日记、归档这些**对象属性**的东西无家可归，只能硬塞进某个主题，污染知识树。
- 主题边界会随兴趣漂移，顶层结构不稳定。

正确做法是顶层按**对象**分区，每个对象是一类"东西的性质"：

| 对象分区 | 性质 | 典型内容 |
|---|---|---|
| 00 系统 | 元层 | 原则、命名、模板 |
| 01 待办 | 输入 | 收件箱、日记、剪藏 |
| 02 战略 | 方向 | 北极星、年度重点、反目标 |
| 05 知识 | 主题 | 12 个主题叶子层（主题只在这里出现） |
| 06 项目 | 执行 | 真实执行单元（data plane） |
| 07 agent | 规则 | 协作规则、skill（control plane） |
| 99 归档 | 冷存储 | 不再活跃但保留 |

**主题只在叶子层出现**（05_ 知识下的 12 个主题），永远不上浮到顶层。这样顶层结构稳定，待办和归档有明确归属，主题漂移只影响叶子。

## OS 是 control plane，项目 repo 是 data plane

这是从网络/系统设计借来的平面划分，落到个人知识治理上：

- **Control plane（控制平面）= OS 本身**：规则、模板、命名、agent 协作规则、skill 注册表、配置层（`.agents/`、`.claude/`、`.obsidian/` 等）。它定义"怎么做事"，本身不产出内容。
- **Data plane（数据平面）= 项目 repo / 执行单元**：自动研究引擎、论文流水线、博士毕业流程这类真实执行单元（落 06_）。它"做事、产出内容"，但规则不在这里定义。

划分的理由：

- **规则与执行解耦**：改规则不会动到执行内容，反之亦然。
- **可复用性**：同一套 control plane 规则能驱动多个 data plane 项目。
- **保护性**：control plane 是高风险区（规则被改坏影响全局），适合配 readonly / fix；data plane 容错性高，可以频繁改动。
- **迁移性**：换平台（Obsidian → 夸克 → GitHub backup）时，control plane 的规则要原样搬走，data plane 的内容按需取舍。

一句话：**规则住在 OS（control plane），执行住在项目（data plane），两者用统一编号缝合。**

## 这套观怎么落到操作上

- 建新仓或迁移时，第一步先定**对象分区**（顶层目录），不要先定主题。
- 执行单元一律进 data plane（06_ 这类），绝不把执行内容塞进 00_/07_。
- 规则、模板、skill、配置进 control plane（00_/07_/配置层），并对它们施加更强的写保护。
- 主题只能在叶子层（如 05_ 知识下的子目录）出现，主题名变了只动叶子，不动顶层。
- raw 层属于"不可再生资产"，按 control plane 级别保护（只追加不覆盖）。

## 适用边界

- 本观面向**单人多项目**的科研知识治理；纯团队协作需补权限、review、分支策略，本页不覆盖。
- "对象 vs 主题"是默认第一性原则，不是唯一原则——当某个主题体量大到自成一个子仓时（如独立的开源项目），可以在 data plane 单列，但顶层仍按对象组织。
- 平面划分是逻辑划分，不要求物理上拆成多个仓库；同一 Obsidian 仓内用目录 + 编号即可表达。
